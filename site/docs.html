DOCUMENTATION / HANDS-ON SETUP

Get from installation to a replayable privacy check.

ShieldSpec is a local developer tool for testing privacy behavior before a Zcash transaction is signed. Start by inspecting known proposal fixtures, then run the real Zcash SDK against controlled wallet states. When two compatible wallet versions disagree, the differential fuzzer can minimize the input and save a reproducible finding.

Follow the guideView source documentation ↗

Test-only synthetic data. No wallet seed phrase, funded account, signing, or broadcasting required.

START HERE

Before you start

Install Git and the Rust toolchain. The repository pins Rust 1.95.0 through rust-toolchain.toml. Your first build needs an internet connection to download dependencies. The real SDK runner takes more time and disk space than the lightweight snapshot checker.

CLONE AND VERIFY
git clone https://github.com/Ay-obami/ShieldSpec.git
cd ShieldSpec
rustc --version

Run the commands below from the repository root. Keep --locked so your dependency graph matches the committed lockfile.

PATH 01 / FASTEST START

Check a snapshot, then compare two

A proposal snapshot describes observable facts about a proposed transaction—for example, whether change would go to a transparent address. ShieldSpec's lightweight CLI checks those facts against configured rules. It does not need a live wallet.

First, verify a known-good fixture

SNAPSHOT CHECK
cargo run --locked -p shieldspec-cli -- \
  check --input fixtures/shielded-payment.json \
  --policy standard --format human

Expected: The fixture passes the configured privacy rules and exits 0.

Next, compare the clean proposal with transparent change

DIFFERENTIAL SNAPSHOT CHECK
cargo run --locked -p shieldspec-cli -- \
  diff --baseline fixtures/shielded-payment.json \
  --candidate fixtures/transparent-change.json \
  --policy standard --format human

Expected: SS003_TRANSPARENT_CHANGE and exit 2. This deliberately failing fixture teaches you what a regression report looks like; it is not a newly discovered Zcash flaw.

PATH 02 / REAL WALLET PROPOSAL MACHINERY

Execute a controlled Zcash SDK campaign

The SDK runner creates synthetic in-memory wallet state, uses the actual Zcash proposal-construction code, then normalizes the result. Here we compare the same runner against itself, so it is a negative control: it demonstrates plumbing and policy observations, not cross-version compatibility.

BUILD AND RUN A TWO-CASE CONTROL
cargo build --locked -p shieldspec-zcash-runner --bins
target/debug/shieldspec-fuzz fuzz \
  --baseline-runner target/debug/shieldspec-zcash-runner \
  --candidate-runner target/debug/shieldspec-zcash-runner \
  --seed 148 --cases 2 --format human

Expected: no_regression_found, exit 0. Wallet-policy counts are zero unless you explicitly enable a named spend policy.

Observe four real Orchard-only spend-policy decisions

This campaign covers Orchard or Sapling funding, before or at NU6.3 activation. The same named SDK policy is observed on both sides. Two Orchard-funded scenarios are accepted; two Sapling-funded scenarios are rejected—equivalent verdicts across identical runners.

NU6.3 FOUR-CASE POLICY CONTROL
target/debug/shieldspec-fuzz fuzz \
  --baseline-runner target/debug/shieldspec-zcash-runner \
  --candidate-runner target/debug/shieldspec-zcash-runner \
  --baseline-arg=--wallet-spend-policy --baseline-arg=orchard-only \
  --candidate-arg=--wallet-spend-policy --candidate-arg=orchard-only \
  --scenario-family ironwood --seed 2026 --cases 4 --format json

Expected: status: no_regression_found, cases_executed: 4, and baseline, candidate, and comparable policy observation counts of 4. The named zcash_spend_orchard_only_v1 spend-source policy is different from historical Zallet FullPrivacy.

PATH 03 / INDEPENDENT VERSIONS

Compare your own wallet builds and replay a difference

For actual regression detection, compile two independent, protocol-compatible runner executables against the versions you intend to compare. Supply the same scenarios and the same explicitly implemented policy name on both sides. Do not infer a wallet's policy decision solely from a snapshot warning.

TEMPLATE — REPLACE BOTH RUNNER PATHS
target/debug/shieldspec-fuzz fuzz \
  --baseline-runner /path/to/baseline-runner \
  --candidate-runner /path/to/candidate-runner \
  --seed 148 --cases 25 --policy standard \
  --save /path/to/discovery.json --format json

Important: This is a template, not a runnable copy-paste command until you replace the executable paths. A discovery file is created only if the engine finds a stable differential and revalidates its minimized case.

REPLAY A SAVED DIFFERENCE
target/debug/shieldspec-fuzz replay \
  --input /path/to/discovery.json --format json

A saved discovery records the original and minimized scenarios, executable hashes, runner arguments, and observed differences. Replay checks that provenance before reporting whether the same result was reproduced. A changed binary or missing policy observation is an operational error, not proof of privacy.

VERIFIED UPSTREAM HISTORY

Reproduce the historical Zallet #677 case

ShieldSpec's general fuzzer automatically detected a real historical FullPrivacy decision difference by invoking two independently compiled, pinned versions of Zallet. The affected code accepted an Ironwood-to-Sapling proposal; the corrected code rejected it. The fuzzer minimized and replayed that difference. It was already documented and fixed upstream—this is a proven regression-test capability, not a new vulnerability disclosure.

This heavier optional path needs Python 3, Git, Rust 1.95.0, network access, native build dependencies, and extra disk space for upstream compilation. From the repo root:

BUILD PINNED ZALLET POLICY RUNNERS & VERIFY
python3 scripts/build_zallet_policy_runners.py \
  --output-dir /tmp/shieldspec-zallet-auto \
  --manifest /tmp/shieldspec-zallet-auto/manifest.json \
  --cargo-target-dir /tmp/shieldspec-zallet-auto-cargo

python3 scripts/make_zallet_immutable_launchers.py \
  --manifest /tmp/shieldspec-zallet-auto/manifest.json \
  --output-dir /tmp/shieldspec-zallet-auto/launchers

cargo build --locked -p shieldspec-zcash-runner --bin shieldspec-fuzz

python3 scripts/verify_zallet_auto_discovery.py \
  --fuzzer target/debug/shieldspec-fuzz \
  --manifest /tmp/shieldspec-zallet-auto/manifest.json \
  --output-dir /tmp/shieldspec-zallet-auto/evidence

Expected: Two agreeing controls, then a genuine historical verdict difference automatically found in the third case, with minimized evidence and verified replay. Inspect the committed full reproduction guide and the successful CI run.

AUTOMATION

Gate snapshot changes in GitHub Actions

Add the lightweight action to a job after checking out your repository. This checks your own normalized proposal fixtures; it does not build or fuzz an SDK wallet. Replace the example baseline/candidate paths with your repository's generated snapshot files.

GITHUB ACTIONS JOB STEPS
- uses: actions/checkout@v4
- name: Check proposal privacy regression
  uses: Ay-obami/ShieldSpec@6abf7995bbf629e1f66219c4322e252b1dc70b3b
  with:
    baseline: fixtures/shielded-payment.json
    candidate: fixtures/transparent-change.json
    policy: standard
    format: sarif

Heads-up: The sample candidate intentionally contains transparent change, so this example fails with exit 2. For a real CI gate, use your own approved baseline and current candidate snapshot. See the complete integration guide.

INTERPRETING RESULTS

Exit codes and evidence

ExitMeaningWhat to do
0No configured failing finding or comparable differenceReview coverage and policy names before treating this as a clean result.
1Input, runner, protocol, or operational errorFix the environment or command. This is not a wallet privacy verdict.
2Privacy-rule finding or actual named wallet-policy differenceInspect both verdicts, policy names, minimized case, and replay. Not every difference is a leak.

ShieldSpec cannot prove that a transaction is anonymous. It tests only the configured properties of the proposals and wallet-policy decisions your campaign exercised.

WHEN THINGS DO NOT MATCH

Troubleshooting

I get exit 2 on the introductory fixture.

That is expected for fixtures/transparent-change.json. The fixture intentionally introduces transparent change; use the first known-good check command to confirm a passing run.

I see zero comparable wallet-policy cases.

You may be running snapshot-only mode. Both runners need an actual observed policy with the same name; enable the opt-in --wallet-spend-policy orchard-only arguments on both runners when exercising the SDK control.

My saved discovery will not replay.

Replay verifies executable hashes and recorded arguments. Restore the original compatible runner binaries, check the saved JSON path, and use the matching scenario family. A changed binary is an error, not a clean privacy result.

Do I need a wallet, funds, or network access to test?

No funded wallet or private key is required. The runner builds synthetic test state. Network access is needed to fetch Rust dependencies and historical source versions during setup, not to sign or broadcast transactions.

OPEN SOURCE · ZCASH DEVELOPER TOOLING

Catch privacy regressions before they ship.

A Zcash transaction can succeed while exposing information it should have kept private. ShieldSpec tests transaction proposals before signing: it runs the same wallet scenario through a baseline and candidate implementation, compares observable privacy behavior and named privacy-policy decisions, then minimizes differences into replayable evidence.

01 / THE PROBLEM

Correct transactions.
Unexpected exposure.

Traditional tests ask if the payment works. Privacy testing must also ask which parts of a transaction became observable—and whether a software change altered that promise.

/ 01
◇

Hidden edge cases

A wallet's choice of inputs, recipients, change outputs, and shielded pools affects what an observer can learn—even if the transaction itself is valid.

/ 02
⇄

Version drift

An SDK update or wallet policy change may quietly alter which proposals are accepted or whether a sensitive output becomes observable.

/ 03
↺

Proof that travels

A useful regression report needs the exact wallet scenario, versions, and a way for another developer to reproduce the difference.

What ShieldSpec checks

Real proposal facts and explicitly observed wallet-policy decisions, with the scope of each check kept visible.

How to run these checks ↗

Observe publicly visible net value when a proposal crosses shielded pools. This is a snapshot warning, not by itself a wallet rejection.

03

Exercise Unified Address choices, Sapling recipients, shielded change, fee accounting, and input selection through real SDK proposals.

04

Named wallet-policy verdicts

Compare actual accept/reject decisions from compatible runners under the same named policy—without guessing a policy decision from a warning.

02 / THE ENGINE

From wallet state
to actionable proof.

The engine creates repeatable scenarios, asks each runner what the wallet would actually propose, and checks both the snapshot and any genuine named policy verdict. When a difference appears, it shrinks the case and saves the evidence.

WHAT YOU GET

A finding another engineer can verify.

When the runners differ, the saved result contains the original and minimized scenario, seed, policy name, runner hashes, exact arguments, and replay outcome. With no detected difference, ShieldSpec reports the tested coverage—it does not certify universal privacy.

OPT-IN POLICY OBSERVATION

Spend-policy decisions, not inferred warnings.

The runner calls the actual pinned SDK SpendPolicy::shielded_pools([Orchard]) restriction with --wallet-spend-policy orchard-only and reports zcash_spend_orchard_only_v1. An adequately funded Orchard wallet is accepted; a Sapling-only wallet is rejected for insufficient permitted funds. Its unrestricted diagnostic snapshot is distinct from the policy verdict.

ShieldSpec compares only matching observed policy names and reports comparable_wallet_policy_cases; zero means no wallet-policy comparison took place. This SDK Orchard-only observation is distinct from Zallet's FullPrivacy and does not reproduce the historical bypass.

05 / GET STARTED

Start with
simple commands.

The published v0.5 CLI lets you initialize a project, test configured snapshots, and compare real SDK or independent wallet builds using short commands. Install with cargo install shieldspec-cli --version 0.5.0 --locked. The developer guide explains the setup, expected results, and advanced controls.

01 / INITIALIZE & CHECK SNAPSHOTS
shieldspec init
shieldspec test

Expected: a passing sample snapshot negative control, exit 0. The generated baseline and candidate are identical and do not come from your wallet. Learn to replace them with actual project snapshots →

02 / REAL SDK CONTROL · FOUR CASES
shieldspec test --compare

First: build the fuzzer and runner from source and configure both runner paths, scenario, and policy in shieldspec.toml. For identical runners, expect a no_regression_found negative control, not proof of cross-version agreement or a wallet audit.

07 / CLARITY MATTERS

A few important details.

Does ShieldSpec prove a transaction is private?

No. It assesses configured privacy properties of observable transaction proposals and reports differences. Passing tests do not guarantee anonymity, metadata protection, or safety across all scenarios.

Does the historical example represent a new vulnerability?

No. Zallet's documented upstream issue was previously fixed. ShieldSpec now automatically rediscovers that historical difference through the general fuzzer by running two real pinned Zallet revisions; it does not claim to find a previously unknown vulnerability. The Orchard-only SDK observation remains a distinct spend policy.

Does the website run live fuzzing in my browser?

No. The historical explorer and NU6.3 control matrix are static explanations. Run actual proposal generation, SDK policy observation, comparison, shrinking, and replay with the Rust binaries on your own machine or in CI.

Does it submit transactions or handle wallet funds?

No. ShieldSpec's current Zcash proposal harness uses synthetic in-memory test state. It does not sign or broadcast transactions.

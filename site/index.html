01 / THE PROBLEM

Correct transactions.
Unexpected exposure.

Traditional tests ask if the payment works. Privacy testing must also ask which parts of a transaction became observable—and whether a software change altered that promise.

/ 01
◇

Hidden edge cases

Wallet state, recipient choice, change routing, and pool transitions combine in ways hand-authored tests may miss.

/ 02
⇄

Version drift

Two SDK or wallet revisions can process a scenario differently without an obvious correctness failure.

/ 03

Hard-to-reproduce failures

A surprising result isn't useful unless another engineer can replay the exact wallet conditions and outputs.

OPT-IN POLICY OBSERVATION

Spend-policy decisions, not inferred warnings.

The runner calls the actual pinned SDK SpendPolicy::shielded_pools([Orchard]) restriction with --wallet-spend-policy orchard-only and reports zcash_spend_orchard_only_v1. An adequately funded Orchard wallet is accepted; a Sapling-only wallet is rejected for insufficient permitted funds. Its unrestricted diagnostic snapshot is distinct from the policy verdict.

ShieldSpec compares only matching observed policy names and reports comparable_wallet_policy_cases; zero means no wallet-policy comparison took place. This SDK Orchard-only observation is distinct from Zallet's FullPrivacy and does not reproduce the historical bypass.

05 / GET STARTED

From clone to
reproducible proof.

Start with a labeled fault-injection demo, then run a four-case NU6.3 control against the real SDK. The latter compares an identical runner with itself: a negative control, not an upstream bug claim.

01 / CLONE & RUN
git clone https://github.com/Ay-obami/ShieldSpec.git
cd ShieldSpec
cargo run --locked -p shieldspec-zcash-runner --bin shieldspec-fuzz -- demo --format human

Expected: an intentionally injected privacy-regression finding and a replay command. Exit code 2 indicates a detected finding.

02 / REAL SDK CONTROL · FOUR CASES
cargo build --locked -p shieldspec-zcash-runner --bins
target/debug/shieldspec-fuzz fuzz \
  --baseline-runner target/debug/shieldspec-zcash-runner \
  --candidate-runner target/debug/shieldspec-zcash-runner \
  --baseline-arg=--wallet-spend-policy --baseline-arg=orchard-only \
  --candidate-arg=--wallet-spend-policy --candidate-arg=orchard-only \
  --scenario-family ironwood --seed 148 --cases 4 --format human

Self-comparison negative control: four deterministic NU6.3 combinations, real SDK Orchard-only spend-policy observations, and no expected differential. Review the reported comparable policy-case count before interpreting a clean run.

07 / CLARITY MATTERS

A few important details.

Does ShieldSpec prove a transaction is private?

No. It assesses configured privacy properties of observable transaction proposals and reports differences. Passing tests do not guarantee anonymity, metadata protection, or safety across all scenarios.

Does the historical example represent a new vulnerability?

No. Zallet's documented upstream issue was previously fixed. ShieldSpec now automatically rediscovers that historical difference through the general fuzzer by running two real pinned Zallet revisions; it does not claim to find a previously unknown vulnerability. The Orchard-only SDK observation remains a distinct spend policy.

Does the website run live fuzzing in my browser?

No. The historical explorer and NU6.3 control matrix are static explanations. Run actual proposal generation, SDK policy observation, comparison, shrinking, and replay with the Rust binaries on your own machine or in CI.

Does it submit transactions or handle wallet funds?

No. ShieldSpec's current Zcash proposal harness uses synthetic in-memory test state. It does not sign or broadcast transactions.
